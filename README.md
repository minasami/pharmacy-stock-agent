# Pharmacy Stock Agent

Built for the Meta Global AI Developer Hackathon (Oct 26, 12:00 PM ET kickoff to Nov 4, 9:00 PM ET, 2026). Every commit in this repo was made during the event. See `BUILT_DURING_EVENT.md`.

A pharmacist photographs a shelf or an opened delivery carton. The agent:

1. finds every pack in the photo with **SAM 3.1** (`sam-3.1`, prompt "medicine box"),
2. reads each numbered pack region with **Muse Spark** (`muse-spark-1.3`) into a strict JSON schema: name, strength, pack size, lot and expiry,
3. matches each pack to the catalog, and sends anything doubtful (low confidence, unreadable lot or expiry, strength mismatch) to a human instead of guessing,
4. flags expired and near-expiry packs (90 days by default; printed MM/YYYY means end of that month),
5. proposes stock changes (receive a delivery, quarantine expired lots) that do nothing until a pharmacist approves them by name, with an audit log,
6. drafts a restock order per supplier from par levels and reorder points. Expired stock does not count. The order is a draft and nothing is sent.

You can run each step yourself, or give the **agent** a goal and let it choose the steps (see [Agent mode](#agent-mode-tool-calling)).

## Ground rules
- **Synthetic data only.** The catalog, makers, suppliers, lots, barcodes (200- in-store prefix) and photos are fictional and generated by `scripts/make_samples.py`.
- **No clinical or substitution advice.** The schema has no fields for uses, doses or alternatives. A deterministic guard (`src/safety/guard.js`, English and Arabic patterns) refuses such questions and blocks any draft that drifts into them. A poor match is never mapped to a "close" product.
- A pharmacist approves every stock change and every order.

## Setup and run
Requires **Node.js 20 or later** (`node --version`). There are no npm dependencies, so there is nothing to install. Python 3 with Pillow is only needed to regenerate the sample photos (`npm run samples`).

```bash
git clone <this repo> pharmacy-stock-agent && cd pharmacy-stock-agent
npm test                      # 53 tests, all offline
npm run check                 # build check: JS syntax, JSON data, zero dependencies
npm run demo                  # end-to-end CLI run on the synthetic photos (replay provider)
AS_OF=2026-10-27 npm run web  # web UI on http://127.0.0.1:8787
```

`AS_OF` pins "today" so the expiry flags in the demo match the recorded sample photos. Without it the real date is used. `PORT` and `HOST` change where the web UI listens (default `127.0.0.1:8787`, local only). Stock, review queue, approvals and the audit log are kept in `state/` (git-ignored); set `STOCK_STATE_DIR` to use another folder, or click **Reset demo data** in the footer.

### CLI
```bash
node src/cli.js reset
node src/cli.js shelf samples/shelf-01.png --as-of 2026-10-27
node src/cli.js delivery samples/delivery-01.png --as-of 2026-10-27
node src/cli.js pending
node src/cli.js approve CS-001 --by "Demo Pharmacist"
node src/cli.js expiry --as-of 2026-10-27
node src/cli.js restock --as-of 2026-10-27 --json
node src/cli.js ask "how many Paracetamol packs do we have?"
node src/cli.js agent "Morning check: audit the shelf, receive the delivery and draft the reorder" \
  --photo samples/shelf-01.png --photo samples/delivery-01.png --max-steps 6 --as-of 2026-10-27
```
Bad input (missing photo, unknown file type, malformed change set id or date) prints the reason and the usage with exit code 2. Configuration errors also exit with code 2.

## Agent mode (tool calling)
Give the agent a goal and up to 4 photos. The planner chooses one tool at a time, reads the result, and chooses the next, until it answers, hands the run to the pharmacist, or hits the step limit (default 6, max 10). Code: `src/agent/tools.js` (tools), `src/agent/loop.js` (loop), `src/agent/planners.js` (planners).

| Tool | What it does | Can it change stock? |
|---|---|---|
| `shelf_audit(photo)` | Shelf photo: detect, read, flag expiry, queue unclear packs | No. It **proposes** a quarantine change set |
| `delivery_intake(photo)` | Delivery carton: count per lot, refuse short-dated lots, queue unclear packs | No. It **proposes** a receive change set |
| `expiry_flags()` | Expired and near-expiry lots in stock | No (read-only) |
| `restock_draft()` | Restock draft per supplier | No (draft only, nothing sent) |
| `request_human_review(note, photo?)` | Hands a concern to the pharmacist and ends the run | No |

Safeguards:
- There is **no approve tool**. Every change set waits for a named pharmacist (Approvals view or `stock-agent approve`).
- Clinical or substitution goals are refused by the deterministic guard **before** the planner is called. Notes and the final answer pass the same guard.
- `photo` is an enum of the attached photo ids, so the model can't point a tool at another file. Arguments are validated before anything runs, and unknown tools or bad arguments come back to the model as errors.
- Each photo is processed at most once per run, so a repeated call can't propose a duplicate change set.
- Every run is written to the audit log with the steps taken and the change sets proposed (`changes: 0`).

Planners:
- **Live (`MODEL_PROVIDER=meta`)**: Muse Spark (`META_AGENT_MODEL`, default `muse-spark-1.3`) on `POST /chat/completions` with `tools`, `tool_choice: "auto"` and `parallel_tool_calls: false`, following the [tool-calling docs](https://dev.meta.ai/docs/tool-calling). Each assistant message with its `tool_calls` goes back into the conversation, followed by one `role: "tool"` message per call. The request shape is tested with a fake `fetch`. **It has not been run against the live API yet.**
- **Offline (default)**: a deterministic mock planner simulates the tool choices from the request wording and the photo names, so tests and the demo run without a key. It is not a model, and the UI and CLI label it as such.

## Mock vs live provider
The provider is chosen once at startup from the environment. The CLI, the web UI header and the server log all show which one is active.

| | `MODEL_PROVIDER=mock` (default) | `MODEL_PROVIDER=meta` (live) |
|---|---|---|
| What it does | Replays the recorded result (`samples/*.truth.json`) for each bundled synthetic photo; agent steps come from the mock planner | Sends the photo to the Meta Model API: SAM 3.1 finds the packs, Muse Spark reads them; Muse Spark chooses agent steps |
| Needs | Nothing: no key, no network | `MODEL_API_KEY` (starts with `LLM_`) and API credits |
| Photos it accepts | Only photos with a recorded `.truth.json` sidecar (the bundled samples); others get a clear "no recorded result" error | Any PNG, JPEG or WebP |
| Cost | Free | Billed per call against your Meta credits |
| Status | Used by all tests and the demo | Request shape tested with a fake `fetch`; **not yet run against the live API** |

Rules:
- `MODEL_PROVIDER` unset: live only if `MODEL_API_KEY` is set, otherwise mock.
- `MODEL_PROVIDER=mock` always wins, even when a key is set.
- `MODEL_PROVIDER=meta` without a key, or any other value, stops at startup with a clear message. It never falls back silently.

```bash
cp .env.example .env              # for reference; the app reads the real environment, not .env
export MODEL_PROVIDER=meta
export MODEL_API_KEY="LLM_..."    # never commit it; .env is git-ignored
AS_OF=2026-10-27 npm run web
```
Optional: `META_BASE_URL`, `META_SAM_MODEL` (default `sam-3.1`), `META_VISION_MODEL` (default `muse-spark-1.3`), `META_AGENT_MODEL` (default `muse-spark-1.3`), `META_TIMEOUT_MS` (default 60000), `NEAR_EXPIRY_DAYS` (default 90).

Live calls time out after `META_TIMEOUT_MS` and are retried twice on HTTP 429 or 5xx, honouring `Retry-After`. A 401 or 403 is not retried and suggests checking the key and billing. The key is redacted from every error message. If a live call fails in the web UI, the scan returns HTTP 502 with the reason and no stock, review or approval state is changed.

## Backup provider: open-weights Muse Spark Open on Baseten
If the Meta Model API cannot be reached (for example, a region where dev.meta.ai is not available), `MODEL_PROVIDER=baseten` runs the pack reads and the agent planner on **Muse Spark Open**, Meta's open-weights model, through [Baseten Model APIs](https://docs.baseten.co/inference/model-apis/overview). Its API is OpenAI-compatible: base URL `https://inference.baseten.co/v1`, Bearer `BASETEN_API_KEY`, `POST /chat/completions`.

```bash
export MODEL_PROVIDER=baseten
export BASETEN_API_KEY="..."      # never commit it
AS_OF=2026-10-27 npm run web
```
Optional:
- `BASETEN_MODEL` (default `meta-models/muse-spark-open-1026`, the slug given for the event. Baseten's docs list `meta-models/muse-spark-open`; if the default is rejected, set that).
- `BASETEN_BASE_URL` (default `https://inference.baseten.co/v1`).
- `BASETEN_REASONING_EFFORT` (`low`, `medium`, `high` or `xhigh`; the model always reasons and defaults to `xhigh`).
- `BASETEN_TIMEOUT_MS` (default 120000).

If `MODEL_PROVIDER` is unset, `MODEL_API_KEY` selects `meta`; otherwise `BASETEN_API_KEY` selects `baseten`.

What differs from the Meta Model API, following Baseten's docs:
- **Reads:** Muse Spark Open has no structured-output or JSON mode on Baseten. The JSON schema is therefore put in the prompt, with no `response_format`. The reply is parsed, and every field is checked in code (`normaliseReadings`). A missing or malformed pack read becomes an unreadable placeholder with confidence 0, which goes to the pharmacist's review queue. Nothing is invented.
- **Planner:** tool calling with `tools` and `tool_choice: "auto"`. `parallel_tool_calls` is not documented for Baseten, so it is not sent. The loop runs one tool per step within the step cap either way. `reasoning_content` is dropped and never shown or sent back.
- **SAM 3.1 is Meta-API-only.** It is not available on Baseten. Pack boxes come from:
  1. SAM 3.1 on the Meta Model API, if `MODEL_API_KEY` is also set. Then any photo works.
  2. Otherwise, the **recorded boxes of the bundled synthetic samples** (the offline fixture sidecars `samples/*.truth.json`). Only the boxes come from the fixture; Muse Spark Open does the reading live. The CLI ("Pack boxes: recorded sample boxes (offline fixture, not SAM)"), the web header and every scan result label this, and each box carries `source: "fixture"`.
  3. Any other photo without SAM is refused with HTTP 422 and a clear message. Regions are never guessed.
- **Status: tested live on Baseten Muse Spark Open (`meta-models/muse-spark-open-1026`) on 2026-10-29.** Shelf audit, delivery intake, the agent planner (it chose shelf_audit → delivery_intake → expiry_flags → restock_draft → final answer), the approval gate and the clinical refusal all ran. The shelf read matched the fixture truth exactly; on the delivery photo one readable pack was sent to human review instead of being received (conservative, not a wrong receive). Pack boxes came from the labelled sample fixtures because SAM is not offered on Baseten. Transcripts: [docs/live-runs](docs/live-runs/). Request shapes are also tested with a fake `fetch`.

Modal also hosts Muse Spark Open on its endpoints. Pointing `BASETEN_BASE_URL` at another OpenAI-compatible host may work, but this is untested and not claimed.

## Web UI
`npm run web` serves a small UI built on `node:http` with plain HTML, CSS and JS. There is no framework and no build step. It binds to 127.0.0.1. It has an agent view and five step views:
- **Agent run**: type a goal, tick sample photos or upload your own, set the step limit, and run. The step trace shows which tool the planner chose at each step and links to the proposed change sets, the review queue and the restock draft.
1. **Scan photo**: pick a sample or upload a photo. Detected packs are overlaid as boxes, coloured OK, near expiry, expired, or needs review (dashed).
2. **Review queue**: unclear packs with a crop of the region and the reasons. A named pharmacist records what is printed on the pack, choosing from the catalog with nothing pre-selected, or sets it aside.
3. **Approvals**: pending change sets. Approve or reject by name, with an audit log.
4. **Inventory & expiry**: every lot with days to expiry and flags, stock levels against reorder points, and a stock-only question box.
5. **Restock draft**: grouped by supplier, downloadable as text. Nothing is sent.

Under the offline replay provider, uploads must be byte-identical copies of the bundled sample photos, because results are replayed from their sidecar files. Live mode reads any photo.

See [Mock vs live provider](#mock-vs-live-provider) to switch to the live Meta Model API.

## Meta Model API usage
- Base URL `https://api.meta.ai/v1` with a Bearer key ([authentication docs](https://dev.meta.ai/docs/authentication)).
- `POST /responses` to `sam-3.1`, sending one user `message` with `input_text` (noun phrase) and `input_image`, as in the [SAM docs](https://dev.meta.ai/docs/sam/overview). The output is box tokens (`<|box;x1=..;y1=..;x2=..;y2=..|>`), parsed in `src/meta/sam.js`.
- `POST /chat/completions` to `muse-spark-1.3`, with an `image_url` data URL and `response_format: json_schema`.
- `POST /chat/completions` to `muse-spark-1.3` with function `tools`, `tool_choice: "auto"` and `parallel_tool_calls: false` for agent step selection ([tool-calling docs](https://dev.meta.ai/docs/tool-calling)).
- **Not yet verified against the live API, because no key was available yet:** the exact non-streaming envelope of the SAM response, whether the JSON schema is honoured for vision, and how well Muse Spark chooses tools for these goals. The code tolerates the common shapes.
